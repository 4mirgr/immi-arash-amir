# انتشار خودکار Worker پس از آزمون‌های معتبر

این مسیر برای همان Worker موجود `immi-arash-amir` در حساب `c570d16fc41cf9f0fa9be67c4bcceafd` آماده است. منبع تازه، سرویس پولی، token مشترک دو پزشک یا مجوز ارسال تازه ایجاد نمی‌کند. فایل‌های آماده: `.github/workflows/deploy-worker.yml` و `scripts/deploy_worker.py`.

## وضعیت فعلی و کاری که صاحب حساب باید انجام دهد

تا ثبت Secret زیر، workflow صریحاً «تنظیم نشده؛ هیچ انتشار انجام نشد» گزارش می‌کند و job انتشار اجرا نمی‌شود. صرف وجود کد، اتصال CI به Cloudflare نیست.

۱. در Cloudflare، از **My Profile → API Tokens → Create Token → Create Custom Token** یک token جدا مخصوص انتشار همین پروژه بسازید. حداقل مجوز مورد نیاز **Account → Workers Scripts → Edit** است؛ Account Resources را فقط روی حساب مالک همین Worker بگذارید. این اسکریپت نه token می‌سازد و نه به ویرایش Zone، DNS، اطلاعات Supabase یا database نیاز دارد. اگر Cloudflare برای حفظ binding موجود D1 مجوز خواندن بخواهد، فقط **D1 → Read** همان حساب اضافه شود؛ به‌روزرسانی داده یا اجرای migration جزو CI نیست.

۲. مقدار token را مستقیم در GitHub ثبت کنید:

https://github.com/4mirgr/immi-arash-amir/settings/secrets/actions

**New repository secret** → نام دقیق `AUS_CLOUDFLARE_API_TOKEN` → مقدار token. مقدار آن را در چت، فایل، Issue یا لاگ نفرستید. tokenهای اتصال Google/LinkedIn یا Secretهای Worker به GitHub منتقل نمی‌شوند؛ فقط credential جداگانهٔ انتشار استفاده می‌شود.

۳. پس از ثبت، یک اجرای مربوط به **push روی main** از workflow `checks` را دوباره اجرا کنید، یا یک تغییر بررسی‌شده را روی main منتشر کنید. فقط اتمام موفق آن بررسی، مسیر انتشار را فعال می‌کند. اجرای PR، fork، branch دیگر یا بررسی ناموفق اجازهٔ انتشار ندارد. workflow روزانهٔ بررسی و اجرای دستیِ checks به‌تنهایی نسخهٔ تازه منتشر نمی‌کنند.

۴. در Actions، workflow **Deploy verified AUS Worker** باید job انتشار موفق و رسید commit/deployment نشان دهد. در حالت token خالی، job تنظیمات فقط وضعیت ناتمام را توضیح می‌دهد و job انتشار **skipped** است؛ آن را انتشار موفق حساب نکنید.

## کنترل‌های انتشار

- کد از همان SHA موفق و مخزن اصلی خوانده می‌شود؛ credential ذخیره‌شدهٔ checkout غیرفعال است و token GitHub فقط مجوز خواندن دارد.
- پیش از ساخت و بلافاصله پیش از upload، HEAD و main دوباره مقایسه می‌شوند. تغییر main باعث توقف نسخهٔ قدیمی می‌شود.
- نصب با `npm ci --ignore-scripts` و ساخت عمومی همان نسخه انجام می‌شود؛ محتوای خصوصی یا فایل import وارد bundle نمی‌شود.
- تنظیمات فعلی از Cloudflare خوانده می‌شوند؛ هشت Secret موجود با `keep_bindings` حفظ می‌شوند و مقدار آن‌ها قابل خواندن یا چاپ نیست. دو binding دیتابیس باید دقیقاً همان شناسه‌های جاری پروژه باشند. سازگاری، محدودیت‌های موجود و تنظیمات runtime حفظ می‌شوند.
- پنج cron موجود پیش و پس از upload کنترل می‌شوند. هیچ API برای تغییر زمان‌بند، ایجاد resource یا نوشتن D1 در اسکریپت وجود ندارد.
- فقط یک upload مجاز است. خطای نامعلوم در انتقال خودکار retry نمی‌شود؛ ابتدا وضعیت واقعی انتشار بررسی شود. خطای post-check ممکن است بعد از انجام upload رخ دهد و نباید «هیچ تغییری انجام نشد» تفسیر شود.
- bundle فراتر از سقف محافظه‌کارانهٔ فعلی پلن رایگان رد می‌شود؛ افزایش پلن خودکار نیست. بدنهٔ upload، token و پاسخ خام خطا چاپ نمی‌شوند؛ رسید فقط commit، شناسهٔ انتشار و هش bundle است.

## migration و baseline

مبنای اولیهٔ schema، commit `d4045d66ae795b80c2a3c51e479783961c4e42d5` است که schemaهای موجودش قبلاً با مسیر مدیریتی بررسی شده‌اند. هر تغییر SQL بعد از آن، از جمله SQL جدول تازه یا migration، انتشار خودکار را متوقف می‌کند. CI هرگز از روی نام فایل فرض نمی‌کند migration اجرا شده است.

وقتی migration جدید لازم شد، ابتدا همان migration با دادهٔ مجاز و بررسی جداسازی مالک به روش مدیریتی اعمال و تأیید شود. سپس Repository Variable با نام `AUS_WORKER_SCHEMA_BASELINE` را روی SHA کاملِ commit حاوی آخرین SQL بررسی‌شده قرار دهید. baseline باید جدِ نسخهٔ هدف باشد. تغییر این متغیر جای اجرای SQL یا تست بازیابی نیست؛ تا تأیید واقعی، baseline را جلو نبرید.

## آزمون و بازیابی

`python -m unittest discover -s tests -p test_worker_deployment.py -v` فقط fixture مصنوعی و API شبیه‌سازی‌شده استفاده می‌کند؛ token و انتشار واقعی لازم ندارد. حالت‌های token مفقود، main تغییرکرده، SQL تأییدنشده، binding ناشناخته، secret/cron تغییریافته و نتیجهٔ نامعلوم upload آزموده می‌شوند.

برای بازگشت کد، commit مشکل‌دار را revert و بررسی‌های main را اجرا کنید؛ یا با اتصال مدیریتی نسخهٔ موفق قبلی Worker را بازگردانید و منبع Git را هم هماهنگ کنید. بازگشت کد، بازگردانی database نیست. تا داشتن credential اختصاصی CI، انتشار مجاز از اتصال مدیریتی فعلی همچنان ممکن است؛ آن را خودکارسازی CI معرفی نکنید.
