# راه‌اندازی پشتیبان خودکار؛ طرح اجرایی مشخص

وضعیت در ۲۰۲۶-۱۱-۰۵: **این طرح هنوز فعال نشده است.** ابزار رمزگذاری و بررسی فایل موجود است؛ گرفتن خروجی کامل از سرور، انتقال زمان‌بندی‌شده به مقصد مستقل و بازیابی واقعی در محیط جدا هنوز به هم متصل نشده‌اند. این سند ادعای ساخت حساب، ذخیرهٔ نسخهٔ واقعی یا اجرای موفق زمان‌بندی ندارد.

## پیشنهاد کم‌هزینه

برای شروع از **Google Drive در حسابی مخصوص نگه‌داری پشتیبان** استفاده شود؛ پوشهٔ خصوصی مخصوص همین سامانه و فایل‌های رمزگذاری‌شده. فضای رایگانِ باقی‌ماندهٔ آن حساب باید پیش از فعال‌سازی بررسی شود؛ رایگان یا نامحدودماندن سرویس تضمین نمی‌شود. این حساب و پوشه نباید عمومی یا به پوشهٔ مکاتبات و مدارک روزمرهٔ دو پزشک متصل باشد. ترجیح، حسابی جدا از حساب مدیریت Cloudflare و GitHub است تا از دست‌رفتن یک حساب همهٔ نسخه‌ها را از دسترس خارج نکند.

تهیهٔ نسخه در یک اجرای زمان‌بندی‌شدهٔ مستقل انجام شود؛ پیشنهاد اول یک مخزن خصوصی مخصوص عملیات پشتیبان در GitHub Actions است، مشروط به بررسی سهمیهٔ رایگان حساب. نسخه‌ها **در Git، لاگ یا artifactهای GitHub قرار نمی‌گیرند**. runner فقط خروجی را در فضای موقت محدود آماده، رمزگذاری، آپلود و سپس صحت فایل آپلودشده را با دانلود و بررسی تأیید می‌کند. پس از پایان، فضای موقت پاک می‌شود. پرشدن سهمیه باید کار را متوقف کند، نه سرویس را خودکار به پلن پولی ببرد.

این روش حضور آنلاین مدیر یا روشن‌بودن مک‌بوک را لازم ندارد. با این حال، زمان‌بندی GitHub می‌تواند تأخیر داشته باشد و نباید به‌عنوان سرویس با زمان اجرای تضمین‌شده معرفی شود. اگر سهمیه یا دسترسی مناسب نبود، همین فرایند قابل انتقال به یک runner مستقلِ مورد اعتماد است؛ خرید سرور پیش‌فرض این طرح نیست.

## دامنهٔ نسخه و جدایی دو حساب

- خروجی خودکار باید از دادهٔ مجاز سرور به‌صورت صفحه‌بندی‌شده گرفته شود؛ نباید endpoint دانلود فعلی با محدودیت ۱۰۰ ردیف در هر جدول را «پشتیبان کامل» نام‌گذاری کرد.
- پروفایل، برنامه‌ریزی، قالب‌ها و پیش‌فرض‌ها، نسخه‌های رزومه، پیش‌نویس‌ها و سوابق خصوصی ضروری برای **هر پزشک در فایل و مسیر جداگانه** قرار گیرند. UUID مالک و رابطهٔ هر ردیف حفظ شود. صندوق دوم امیر به همان مالک و mailbox مستقل خودش وصل می‌ماند.
- آگهی‌ها و بانک عمومی مراکز، خروجی جدا دارند؛ دادهٔ خصوصی مکاتبات وارد آن نمی‌شود. دادهٔ عمومی قابل بازجمع‌آوری است، اما تاریخچه و منشأ آن باید در تصمیم نگه‌داری لحاظ شوند.
- سوابق ارسال، fingerprintها و فهرست ممنوعیت ارسال نگه داشته شوند تا پس از بازیابی، درخواست تکراری ارسال نشود.
- توکن Google/LinkedIn، OAuth state، بلیت ورود، نشست‌ها و تأییدهای آمادهٔ ارسال در نسخهٔ قابل بازیابی عملیاتی **وارد نمی‌شوند**. پس از حادثه اتصال سرویس‌ها دوباره تأیید می‌شود. فایل backup با تغییر نام نباید به اعتبارنامهٔ سرویس تبدیل شود.
- فایل‌های PDF/DOCX و اصل مدارک در Drive خودبه‌خود داخل خروجی JSON نیستند؛ فهرست نسخه باید صریح بگوید کدام فایل واقعاً کپی شده و کدام فقط پیوند است. کپی فایل‌ها مرحلهٔ جدا با رضایت و ظرفیت مشخص است.

برای هر اجرا، manifest رمزگذاری‌شده شامل نسخهٔ schema، شناسهٔ سامانه، زمان شروع و پایان، تعداد ردیف هر جدول، محدودهٔ هر مالک و هش فایل‌ها ثبت شود. نبود صفحه، اختلاف شمارش، محدودشدن خروجی یا خطای دانلود، وضعیت اجرا را «ناقص» می‌کند؛ نسخهٔ ناقص جای آخرین نسخهٔ سالم را نمی‌گیرد. از آنجا که Supabase و D1 یک تراکنش مشترک ندارند، پنجرهٔ زمانی تهیهٔ نسخه باید ثبت شود و سازگاری روابط پس از استخراج کنترل شود.

## کلید و دسترسی؛ چه چیزهایی باید آماده شوند؟

۱. حساب مقصد، یک پوشهٔ خصوصی و مجوز محدود ساخت/خواندن فایل‌های همان برنامه لازم است. اتصال جدید مقصد با رضایت مالک حساب انجام می‌شود؛ token موجود Gmail پزشکان کپی یا به‌عنوان fallback استفاده نمی‌شود. رضایت Google و ذخیرهٔ refresh token در محل Secret را باید صاحب حساب تأیید کند؛ هیچ رمز یا token در چت فرستاده نمی‌شود.

۲. دریافت دادهٔ سرور به یک مسیر اختصاصی و حساب فقط‌خواندنیِ محدود به جدول‌های تأییدشده نیاز دارد؛ کلید مدیر Supabase یا دسترسی تغییر/حذف دیتابیس را برای سهولت در job عمومی قرار نمی‌دهیم. این exporter هنوز باید ساخته و در برابر دسترسی به مالک اشتباه، صفحه‌بندی ناقص و schema ناشناخته آزمایش شود. از publishable key یا نشست کوتاه‌مدت مرورگر نمی‌توان پشتیبان unattended کامل ساخت.

۳. گذرواژهٔ تصادفیِ مستقل برای رمزگذاری ایجاد و در Secret اجرای پشتیبان نگه‌داری می‌شود؛ نسخهٔ بازیابی آن در password manager مستقل با بازیابی امن و دسترسی محدود ذخیره می‌شود. کلید نباید کنار فایل Drive یا داخل Git باشد. ابزار Python موجود گذرواژه را از descriptor دریافت می‌کند؛ آن را در آرگومان فرمان، خروجی job یا فایل workflow نمی‌گذاریم. گم‌شدن کلید یعنی فایل رمزگذاری‌شده قابل بازیابی نیست.

۴. نام‌گذاری، گزارش موفقیت و هشدار فقط شناسهٔ اجرا، زمان، شمارش و خطای فنیِ پالایش‌شده را نشان می‌دهند؛ نام بیمار، متن ایمیل، آدرس مقصد و رمز نمایش داده نمی‌شوند. هشدار شکست یا قدیمی‌شدن نسخه به مدیر عملیات می‌رود؛ پیام‌های خصوصی دو پزشک به گروه مشترک منتقل نمی‌شوند.

## زمان‌بندی و نگه‌داری پیشنهادی

- شروع با یک نسخهٔ شبانه در ساعت ۰۳:۳۰ تهران، به‌علاوه پیش از migration یا import حساس؛ پس از برآورد اندازه و سهمیه اجرا شود.
- نگه‌داری پیشنهادی: ۷ نسخهٔ روزانه و ۴ نسخهٔ هفتگی؛ تنها نسخه‌های کامل و بررسی‌شده در چرخش سالم حساب می‌شوند. پاک‌کردن نسخه‌های قدیمی بعد از تأیید نسخهٔ جدید انجام شود و آخرین نسخهٔ سالم هرگز با شکست job حذف نشود.
- با ظرفیت فعلی ابزار Python، حداکثر ۱۲۸ فایل JSON و مجموع ۱۶ MiB دادهٔ خام پشتیبانی می‌شود. بزرگ‌شدن داده باید به پارت‌های مستقل با manifest کلی یا ابزار snapshot مناسب منجر شود؛ تقسیم خام بدون کنترل مالک/تمامیت مجاز نیست.
- وضعیت پنل باید «آخرین نسخهٔ سالم»، «اندازه»، «پوشش»، «آخرین آزمون بازیابی» و «نیاز به رسیدگی» را نشان دهد؛ صرفاً ذخیره‌شدن تنظیمات، نشان سبز فعال‌بودن نیست.

## آزمون بازیابی واقعی چگونه انجام می‌شود؟

ابتدا همین رمزگذاری با دادهٔ کاملاً ساختگی و دو UUID ساختگی آزموده می‌شود. سپس در یک محیط جدا، PostgreSQL با schema/RLS واقعی و SQLite سازگار با جداول خصوصی ساخته می‌شوند. هیچ اتصال شبکه‌ای به Gmail، LinkedIn یا ارسال Telegram فعال نمی‌شود و هیچ cron یا صف ارسال اجرایی وجود ندارد. ساخت branch پولی Supabase شرط این آزمون نیست؛ محیط محلی/موقت جدا برای شروع کافی است.

در آزمون، فایل از مقصد واقعی دانلود و صحت رمز و manifest بررسی می‌شود؛ ردیف‌ها در **دیتابیس جدید و خالی** وارد می‌شوند و شمارش، روابط و schema کنترل می‌شوند. نشست امیر باید فقط ردیف‌های خودش و نشست آرش فقط ردیف‌های خودش را ببیند؛ mailbox ثانویهٔ امیر نباید در دسترس آرش باشد. آزمون مستقیم RLS با نقش/claim واقعی ضروری است؛ فیلتر ظاهری صفحه یا صرف بازکردن فایل این موضوع را ثابت نمی‌کند.

تأییدها و زمان‌بندی‌های ارسال پس از بازیابی غیرفعال می‌مانند؛ suppression و fingerprintها حفظ می‌شوند؛ اتصال سرویس‌ها نیازمند رضایت تازه است. فقط بعد از این آزمون و ثبت گزارش بدون دادهٔ خصوصی، می‌توان «قابلیت بازیابی آزمایش‌شده» نوشت. بازیابی روی اطلاعات اصلی اقدام جداگانه و نیازمند طرح مشخص برای همان حادثه است.

## گام بعدیِ لازم از طرف کاربر

حساب Google مقصد پشتیبان را تعیین کنید؛ بهتر است حساب مستقلی باشد که بازیابی و دسترسی آن در اختیار خودتان است. سپس مسیر امن اتصال و ثبت Secret آماده می‌شود و رضایت Google را در همان صفحهٔ رسمی انجام می‌دهید. **رمز، گذرواژهٔ پشتیبان یا token را در چت نفرستید.** تا ساخته‌شدن exporter، اجرای منظم موفق و آزمون بازیابی، وضعیت پشتیبان خودکار همچنان «راه‌اندازی نشده» می‌ماند.

## ابزار موجود و بررسی فعلی

راهنمای فرمت و عملیات محلی در [BACKUP-RESTORE.md](BACKUP-RESTORE.md) است. `scripts/backup_private.py` و `scripts/restore_private.py` خروجی JSON آماده‌شده را رمزگذاری/بررسی می‌کنند؛ هیچ کدام خودشان exporter سرور، uploader یا scheduler نیستند. فرمت مرورگر با فرمت Python متفاوت است و نباید جای هم استفاده شوند.
