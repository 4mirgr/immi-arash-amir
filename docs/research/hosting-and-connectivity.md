# Cost and connectivity decisions

Architecture proposal, 2026-11-03; no hosting account has been provisioned and no free-tier quota has been independently verified in this pass.

Start with a portable React frontend and server API; retain SQLite for the local prototype. Before public use, deploy verified authentication, per-user server authorization, encrypted secret storage, backups, audit events and HTTPS. Production may use managed Postgres/Supabase with row-level security or a separately hosted portable API/database. Do not publish CVs, imported spreadsheets, contact database or OAuth refresh tokens to GitHub or a public static bundle.

Cloudflare Pages/Workers or another static host can be evaluated for the frontend and gateway; Supabase can be evaluated for auth/database/private storage. Free plans have quotas, suspension and availability constraints. No guarantee of permanently free AI, continuous crawling, storage or email throughput. Configure budgets, request limits, bounded scheduled jobs, deduplication and source-specific backoff. A 10-second dashboard refresh queries stored results; it must not imply crawling every source every 10 seconds. AI providers remain optional adapters, with an explicit disconnected state until credentials and quotas are known.

For an eventual .ir domain, keep NIC domain registration, DNS authority, TLS issuance, hosting eligibility, user access from Iran, outbound server access and Google OAuth domain verification as separate checks. A .ir domain does not guarantee any provider will serve or accept the project. Test actual provider terms and connectivity from the intended networks before choosing a host. Keep assets first-party, cache permitted public metadata, provide retry queues and permit migration to another compliant host. Do not promise a proxy can solve every filtering, provider-policy or regional restriction; do not bypass provider access controls. Credentials and private documents must never be routed through an untrusted proxy.

Integrations still need user-owned setup: Google Cloud OAuth project/consent and redirect URIs with separately authorised Gmail, Drive and Calendar scopes for each user; Telegram bot/chat authorisation; hosting/database account; an AI API account if used; NIC domain/DNS control. Request credentials through secrets configuration, never commit them or request they be pasted into repository files. Google Calendar two-way sync needs provider identifiers, sync tokens, conflict handling and webhook renewal; Gmail requires thread/message IDs, idempotency and an outbox. These integrations are not implemented by this document.
