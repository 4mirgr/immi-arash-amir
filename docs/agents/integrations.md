# Integrations
Read docs/POLICY.md before external actions. OAuth and credentials server-side; least scopes per action, encrypted refresh tokens, isolated per owner. Gmail watch/history and Calendar sync tokens need renewal and expiry handling. Telegram bot recipient allowlist. Queue idempotent send jobs with bounded retries. Service adapters expose honest disconnected status. No broad account access implied by an installed chat connector. Production requires deployed callback URLs and user consent.

Mandatory Google boundary: two distinct Google identities and independent consent/token sets, mailbox data, sync/watch cursors, extraction/ranking, presets and send queues. One OAuth client may serve both, but never one shared mailbox/token. Derive owner from verified session; enforce unique Google subject binding; fail closed per owner on disconnect. Keep private email-derived findings outside shared clinics unless explicitly shared. Verify cross-account denial and that disconnecting one account leaves the other unaffected. See docs/POLICY.md “Separate Google systems”.

Implementation entrypoints: cloud/google-oauth.mjs (encrypted D1 grant), google-mail.mjs (private cache/ranking), google-send.mjs (explicit queued transport), google-services.mjs (Calendar/Drive). Coordinator wires cloud/worker.mjs. D1 GOOGLE_DB schema files are versioned; existing installations need google-send-replies.sql once, fresh installs use final schemas. Preserve existing secret_text bindings on deployment; never regenerate GOOGLE_TOKEN_KEY if token rows exist. Provider client setup/consent is still required. See docs/GOOGLE.md for setup, docs/STATUS.fa.md for remaining commitments.
