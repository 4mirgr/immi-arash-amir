# Private LinkedIn workspace

`cloud/linkedin-workspace.mjs` implements planning, copyable profile suggestions, private networking notes and a manual-publication content calendar. It **does not connect to LinkedIn OAuth, fetch live analytics, scrape connections, edit profiles or publish posts**. Those capabilities are false in every workspace response. Scheduled posts are explicitly `scheduled_for_manual_publication`; time passing cannot mark them published.

Use the server-only `GOOGLE_DB` D1 binding with `cloud/linkedin-schema.sql`. The `linkedin_*` tables are separate from Gmail data and every query is scoped by the authenticated app owner. Profile URL is loaded from that owner's Supabase `immi_profiles.data.linkedinUrl`. It is a saved public profile link, not proof of a provider connection. URLs, dates, field sizes, profile selectors and cross-origin writes are validated. No browser-supplied owner is accepted.

## Routes

All routes require coordinator-authenticated `{userId,profileId,rest}` and live under `/api/linkedin/`.

- `GET workspace`: profileUrl, capabilities, sections, recommendations, postSuggestions, drafts, posts, metrics, metricsSummary, contacts, tasks and analysis provenance.
- `POST sections {section,currentText}`: current headline/about/experience snapshot, explicitly `user_entered`.
- `GET/POST drafts`: create immutable `{kind,name,text}` revisions. Kind is headline/about/experience/post.
- `GET/POST posts`: `{title,text,scheduledFor?,timezone?}`. Timezone is required with a future ISO timestamp. No provider write occurs.
- `POST posts/:id/schedule {scheduledFor,timezone}`: reschedule an unpublished owned draft.
- `POST posts/:id/published {publishedUrl?}`: records the user's report, with `publicationEvidence:'user_reported_not_provider_verified'`. It does not verify publication.
- `GET/POST metrics`: optional integer `connections`, `followers`, `profileViews`, `searchAppearances`, plus required `asOf`. Missing values remain absent, not fabricated zero. Workspace deltas use only fields present in both latest manual snapshots.
- `GET/POST contacts`: `{name,profileUrl,role?,organization?,purpose?,status?,notes?}`. Purpose: job/university/research/supervision/other. Status: to_research/to_contact/contacted/replied/follow_up/closed.
- `POST contacts/:id {status,notes?}`: private follow-up status update. Contacts are user-entered research targets, not a downloaded or verified connection graph; no message is sent.

Recommendations are conservative rule-based working text derived from private profile direction. A resident remains a resident, incomplete training is not a specialist award, and no board/English/AMC result is invented. All replacements and original post ideas require user review. Profile-section coverage counts only provided local snapshots; it is not a LinkedIn-provided profile score. No image is claimed generated by this module.

## Provider access boundaries

Official LinkedIn documentation retrieved 2026-11-03:

- [Sign In with LinkedIn using OpenID Connect](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2): `openid`, `profile` and `email` provide sign-in and limited identity details. These are not permission to edit the profile or read the member's private graph/analytics.
- [Share on LinkedIn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin): `w_member_social` is required to create a post on behalf of an authenticated member. A developer application/product grant and that individual member's OAuth consent are needed. It is not supplied by this chat's profile link or existing Google connection.
- [Connections API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/connections-api): use is restricted to developers approved by LinkedIn and subject to their data agreements. First-degree graph access must not be promised to a standard OIDC client.

Member analytics and profile editing require separately supported APIs/products; absence of an approved grant is not permission to scrape private pages or automate password-based browser actions. Current workspace functionality is useful without those grants while exposing its manual provenance honestly. Future real publishing must add separate owner tokens, explicit authorization policy, idempotency/unknown-outcome handling and safe media upload; it must never relabel manual scheduling as automatic publication.

## Checks

`node --test tests/cloud_linkedin.mjs` covers owner isolation, no network/provider writes, immutable draft revisions, future/timezone validation, manual evidence labels, nonfabricated metrics, contact follow-up ownership and URL validation. These tests do not establish a live LinkedIn connection.

## Private Connections CSV import

`POST /api/linkedin/contacts/import {csv}` accepts a user-selected LinkedIn Connections export only (UTF-8 CSV up to 500,000 bytes, at most 1,000 data rows). It locates `First Name,Last Name,URL` headers after optional introductory rows/BOM and handles quoted commas/newlines. Known columns include Company, Position and Connected On. Email Address is deliberately ignored. Malformed URLs, empty names and oversized fields are counted as skipped; normalized profile URLs are deduplicated both within the file and against that owner's existing records. Existing names, notes and follow-up status are never overwritten by a repeated import.

The response reports imported/duplicate/skipped counts, reasons, `liveSync:false` and `emailsImported:false`. Imported records carry `source:'linkedin_connections_csv'`, not API verification. No connection invitations or messages are sent. The bulk insert uses parameterized `json_each` with an owner predicate and an atomic existence check; CSV text is never executed as SQL or code. The expression index at the end of `linkedin-schema.sql` can be applied additively to existing installations.

Workspace previews at most 200 contacts and exposes `contactsTotal`. For the full private list, `GET /api/linkedin/contacts` supports `q`, `purpose`, `status`, `limit` (1–200) and `offset`, returning `{contacts,total,limit,offset,connectionsSync:false}`. Imported row counts are not substituted for current LinkedIn connection statistics.

## Provider publication evidence overlay

When the optional LinkedIn OAuth transport tables are installed, owned provider attempts are overlaid as `post.providerPublication` (status, URN, timestamp, pinned author subject and evidence source). `manualActionsBlocked` is true for acknowledged publication, sending, unknown delivery or an unrecognized attempt status. Such posts no longer appear as pending manual-publication tasks, and manual reschedule/report-published endpoints return a conflict instead of encouraging duplicates. A terminal explicit provider failure is not fabricated as publication and may still be handled manually. Missing optional transport tables yield no provider evidence; unexpected database failures fail closed. Evidence from another owner cannot affect this owner's workflow.
